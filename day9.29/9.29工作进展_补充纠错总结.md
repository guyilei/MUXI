## 二、GPU 软件组织与硬件结构

原先写成：

```text
CUDA Core → Thread → Warp → Block → SM → Grid
```

这个顺序容易产生误解，因为它把“软件中的任务组织”和“GPU 的硬件结构”混在了一起。

### 1. 软件中的任务组织

```text
一次 Kernel 启动
        ↓
Grid（整个任务）
        ↓
多个 Block（线程块）
        ↓
多个 Thread（线程）
```

- **Kernel**：所有 GPU 线程共同执行的一份程序。
- **Grid**：一次 Kernel 启动产生的全部 Block。
- **Block**：一组线程，是 GPU 向 SM 分配任务的基本单位。
- **Thread**：逻辑上的工作单元，通常负责一部分数据。
- **Warp**：NVIDIA GPU 硬件把同一个 Block 中的线程进一步组成 Warp 来调度；常见大小为 32 个线程。Warp 通常不由程序员直接创建。

### 2. GPU 的硬件结构

```text
GPU
 └── 多个 SM
      ├── CUDA Core / 普通计算单元
      ├── Tensor Core（部分架构具有）
      ├── 寄存器
      ├── Shared Memory
      └── Warp 调度器等
```

- **SM**：GPU 中负责接收和执行 Block 的主要硬件单元。
- **CUDA Core**：NVIDIA GPU 中执行普通算术指令的硬件计算单元。
- **Tensor Core**：专门加速矩阵乘加等运算的硬件单元。

### 3. 软件任务如何映射到硬件

```text
Grid 中的 Block
        ↓ 调度
GPU 中的 SM
        ↓
Block 内的线程被组织成 Warp
        ↓
SM 内的计算单元执行指令
```

更准确地说：Block 会被调度到某个 SM，并在该 SM 上完成执行；如果寄存器和共享内存等资源足够，一个 SM 可以同时驻留多个 Block。Block 的实际执行顺序和是否同时运行不能由程序假定。

> 注意：今天在 Mac 上使用的是 OpenCL。OpenCL 中的 Work-group 对应 CUDA 中的 Block，Work-item 对应 Thread。沐曦设备的实际线程执行分组应以沐曦架构文档为准，不能直接假定与 NVIDIA Warp 完全相同。

## 三、Kernel 的本质

今天得到的核心认识：

> **Kernel 是所有 GPU 线程共同执行的一份程序，它规定每个线程负责哪份数据，以及怎样处理这份数据。**

一个简单 Kernel 通常包含两部分：

```text
1. 根据 Block 编号和线程编号找到自己负责的数据
2. 对这份数据执行具体计算
```

矩阵加法 Kernel：

```cpp
__kernel void matrix_add(__global const float* A,
                         __global const float* B,
                         __global float* C) {
    int block_col  = get_group_id(0);
    int block_row  = get_group_id(1);
    int thread_col = get_local_id(0);
    int thread_row = get_local_id(1);

    int col = block_col * 2 + thread_col;
    int row = block_row * 2 + thread_row;
    int i = row * 4 + col;

    C[i] = A[i] + B[i];
}
```

其中：

```text
block_col / block_row   → 当前是第几个 Block
thread_col / thread_row → 当前线程在 Block 内的位置
row / col               → 当前线程在整个矩阵中的位置
i                       → 矩阵展开成一维数组后的下标
```

最终每个线程只执行一个位置的加法：

```cpp
C[i] = A[i] + B[i];
```

## 四、Block 切分与 Thread 划分实验

实验输入是两个 `4×4` 矩阵，共有 16 个元素。

线程配置：

```cpp
const size_t total_threads[2] = {4, 4};  // 整体 4×4，共 16 个线程
const size_t one_block[2] = {2, 2};      // 每个 Block 2×2，共 4 个线程
```

由此得到：

```text
横向 Block 数 = 4 ÷ 2 = 2
纵向 Block 数 = 4 ÷ 2 = 2
Block 总数    = 2 × 2 = 4

每个 Block 的线程数 = 2 × 2 = 4
总线程数             = 4 × 4 = 16
```

矩阵切分如下：

```text
┌─────────────┬─────────────┐
│ Block(0,0)  │ Block(0,1)  │
│ 2×2 个元素   │ 2×2 个元素   │
├─────────────┼─────────────┤
│ Block(1,0)  │ Block(1,1)  │
│ 2×2 个元素   │ 2×2 个元素   │
└─────────────┴─────────────┘
```

例如某个线程的信息是：

```text
block_row  = 1
block_col  = 0
thread_row = 1
thread_col = 1
```

它负责的矩阵位置为：

```text
row = 1 × 2 + 1 = 3
col = 0 × 2 + 1 = 1
i   = 3 × 4 + 1 = 13
```

因此这个线程执行：

```cpp
C[13] = A[13] + B[13];
```

也就是逻辑矩阵中的：

```cpp
C[3][1] = A[3][1] + B[3][1];
```

## 五、CPU 启动 GPU Kernel 的基本流程

### 1. 找到并连接 GPU

```text
platform → OpenCL 平台/驱动入口
gpu      → 选中的 GPU 设备
context  → 管理 GPU、程序和内存的运行环境
queue    → CPU 向 GPU 提交任务的命令队列
```

### 2. 创建、编译 Program，并取得 Kernel

```text
gpu_code（OpenCL 源代码字符串）
        ↓ clCreateProgramWithSource
program（OpenCL 程序对象）
        ↓ clBuildProgram
编译成当前 GPU 可以执行的程序
        ↓ clCreateKernel("matrix_add")
kernel（CPU 端代表 matrix_add 的对象）
```

需要区分两次编译：

```text
clang++：编译 CPU 端的 C++ 主程序
clBuildProgram：程序运行时编译 GPU 端的 OpenCL Kernel
```

### 3. 准备 GPU 内存并传递参数

```text
CPU 数组 A、B
        ↓
GPU 内存 gpu_A、gpu_B

GPU 为输出分配 gpu_C
```

`gpu_C` 创建时使用 `nullptr`，表示只分配空间，不需要从 CPU 复制初始结果；Kernel 后续会把结果写入其中。

`clSetKernelArg` 的作用是给 Kernel 传参：

```text
gpu_A → matrix_add 的第 0 个参数 A
gpu_B → matrix_add 的第 1 个参数 B
gpu_C → matrix_add 的第 2 个参数 C
```

### 4. 设置 Block 和 Thread，并提交 Kernel

```cpp
clEnqueueNDRangeKernel(...);
```

这一步把 Kernel 执行命令放入 GPU 的命令队列，并指定：

```text
使用二维线程布局
整体线程布局为 4×4
每个 Block 的线程布局为 2×2
```

`Enqueue` 表示“放入队列”。CPU 提交命令后，GPU 不一定已经立即完成计算。

### 5. 把结果取回 CPU

```cpp
clEnqueueReadBuffer(..., CL_TRUE, ...);
```

它把 `gpu_C` 复制回 CPU 数组 `C`。其中 `CL_TRUE` 表示阻塞读取：如果 GPU 还没有完成前面的 Kernel，CPU 会在这里等待。

因此更准确的性能表述是：

> CPU 与 GPU 间的数据传输以及等待同步可能成为瓶颈，但必须通过计时或 Profiler 确认，不能只看到一次拷贝就认定存在瓶颈。

### 6. 释放资源

程序结束前释放 GPU Buffer、Kernel、Program、Queue 和 Context。

## 六、从矩阵加法对应到 BatchNorm Kernel

今天的矩阵加法虽然简单，但和实际 BatchNorm Kernel 使用的是同一套执行思想。

矩阵加法：

```cpp
int row = block_row * block_height + thread_row;
int col = block_col * block_width + thread_col;
int i = row * matrix_width + col;
C[i] = A[i] + B[i];
```

BatchNorm Kernel：

```cpp
int h_idx = blockIdx.y * blockDim.y + threadIdx.y;
int w_idx = blockIdx.x * blockDim.x + threadIdx.x;
```

两者都在解决：

> 当前线程负责整个数据中的哪个位置？

区别在于 BatchNorm 处理的是多维 Tensor，需要进一步根据 `n、c、d、h、w` 和 stride 计算一维内存下标 `x_idx/y_idx`，然后执行：

```text
读取 x
读取 mean / variance / scale / bias
执行 BatchNorm 计算
处理 alpha / beta
把结果写入 y
```

因此，今天的小实验是在学习工业 BatchNorm Kernel 的执行骨架。

## 七、与大模型推理岗位的关系

大模型推理岗位的主要目标是：

> 让训练好的模型在 GPU 上运行得更快、占用更少显存、支持更高并发并降低成本。

常见工作包括：

```text
模型部署：PyTorch、Transformers
推理框架：vLLM、SGLang
显存优化：KV Cache、PagedAttention
服务调度：Continuous Batching
低精度与量化：FP16、BF16、FP8、INT8、INT4
多卡推理：Tensor Parallel、Pipeline Parallel、通信优化
性能分析：Profiler、时间线、吞吐和延迟分析
算子优化：CUDA/MXMACA、Triton、算子融合
```

今天的工作位于其中较底层的“GPU 编程与算子”部分：

```text
Qwen / Llama
      ↓
vLLM / SGLang
      ↓
PyTorch / 推理算子
      ↓
DNN 库 / GPU Kernel       ← 今天正在学习这里的基础
      ↓
GPU 硬件
```

这意味着今天的矩阵加法不是直接在做大模型推理服务，但它是理解 MatMul、Attention、BatchNorm、算子融合和性能优化的基础。

## 八、需要纠正和补充的地方

1. `CUDA Core、Thread、Warp、Block、SM、Grid` 不能写成一条简单的包含链；软件任务组织与硬件结构要分开描述。
2. Kernel 不只是“找到线程该做什么”，完整含义是“确定线程负责的数据，并规定对数据执行的计算”。
3. Block 是线程分组，也是调度到 SM 的基本单位；Thread 才是具体处理数据的逻辑工作单元。
4. OpenCL 中正式名称是 Work-group 和 Work-item，本实验借用 Block 和 Thread 帮助理解 CUDA/MXMACA 风格代码。
5. 当前 `2×2=4` 线程的 Block 适合教学，但不代表真实性能配置。实际 Block 大小要结合硬件、数据规模、寄存器、共享内存和性能测试决定。
6. 当前矩阵尺寸刚好能被线程布局覆盖，因此没有越界。通用 Kernel 应增加边界判断：

```cpp
if (row < rows && col < cols) {
    C[row * cols + col] = A[row * cols + col] + B[row * cols + col];
}
```

7. 为学习而暂时去掉错误检查可以降低阅读负担；正式代码应恢复 OpenCL 返回值检查和 Kernel 编译日志，否则出错时难以定位原因。

## 九、今日总结

今天已经完成了从“知道 GPU 有很多线程”到“能够解释线程如何定位并处理数据”的过渡。

核心结论：

> CPU 负责准备数据和启动 Kernel；GPU 将一次 Kernel 任务组织成 Grid 和 Block；每个 Thread 根据 Block 坐标和组内线程坐标计算自己负责的数据位置，再执行 Kernel 中规定的运算。

当前已经能够解释：

- Kernel、Grid、Block、Thread 的基本关系；
- `block × block_size + thread` 的索引思想；
- `4×4` 矩阵如何切成 4 个 `2×2` Block；
- OpenCL 主程序从连接 GPU 到取回结果的完整流程；
- 简单矩阵加法和实际 BatchNorm Kernel 的对应关系；
- GPU Kernel 基础与大模型推理算子优化之间的联系。
